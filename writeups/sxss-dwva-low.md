# Stored XSS - DVWA (Low)

**Summary:** The current application directly appends the user's input to the page's HTML code. This means the user can add their own HTML and JavaScript code to the application input, and since user input is stored on the server this means that any injected payloads will be executed any time a user opens the application.

**Severity:** Critical - user can extract cookies and log in as other users without needing additional authentication simply as a result of the user viewing the webpage

**Affected component:** The "Name" and "Message" input box fields

**Description**: The application shows the user two fields for a guestbook - one for the name of the guest (which has a max length of 10 characters), and one for a message when they sign in. Once the user has entered text into both fields, they can 'sign' the guestbook to add the guest to the guest list stored on the application which is displayed every time the webpage is opened. Because these fields are stored directly in the HTML/JavaScript code for the webpage, they are output onto the page every time it is opened, meaning that the user can inject their own code onto the site and the application will execute it every time the page is opened.

**Steps to reproduce**: 
1. Enter `<b>test</b>` into both input boxes. This confirms that HTML tags can be injected into them, as both "test"s along with "Message:" will appear in bold and all text will be displayed on the same line.
2. Using a network traffic managing software like Burp, catch the forwarding request generated by signing the guest book and edit the name variable to contain the payload `<script>alert('XSS')</script>`, something which you normally couldn't enter due to the max length limiter on that field. This will cause the webpage to generate an alert every time it is opened.
3. Reload the guestbook page. This will cause the alert to fire again, confirming it's stored on the server and is served to every visitor.

**Impact**: Because the user can run JavaScript code on the application, they could write a program which steals the user's cookies. Because this payload runs every time the application is opened,  this vulnerability affects all users of the webpage (including high-privilege users such as administrators), and could be used to steal a user's cookies when they view the webpage, allowing the attacker to collect them and log in as other users simply through people using the application as intended, completely bypassing additional security measures like passwords and MFA.

**Remediation**: Applying encoding which takes place on output would cause the tags to be displayed as literal text inside the HTML page, stopping code from being injected like this. Input validation could also be implemented as a secondary security measure, and HttpOnly cookies and CSP would allow for extra defense if an XSS attack breaks through the other measures.
